# CLAUDE.md — SpAM_Task

Online Spatial Arrangement Method (SpAM) task for collecting human perceptual similarity judgements
over 725 object images. Built with jsPsych, hosted on Pavlovia, recruiting via Prolific.

> **Full research & implementation plan**: `PLAN.md` at the repo root (gitignored — not yet published).
> Read it before making significant changes to parameters, QC logic, or trial design.

---

## Status

**Deployed — task version 4.0** (`deployment.version: "4.0"`, `deployment.mode: "production"`).
All JS modules, the HTML entry point, and `generate_manifest.py` are complete; Prolific completion
codes are populated for all three exit paths (complete / screened-out / no-consent).

The v4.0 design is a **preliminary screening stage of 8 main trials (6 distinct + 2 verbatim
repeats) plus 1 catch trial**, followed by the experimental stage (12 distinct + 2 repeats + 2
catch). Screening excludes on *behaviour* (move count, arrangement spread) and *performance*
(test-retest reliability of the 2 repeats) — see "Live screening" and the `screening_block` table.

When re-deploying after any change:
1. Re-run `python generate_manifest.py` from `SpAM_Task/` if the stimulus directories changed
2. Bump `deployment.version` **and** the matching `?v=` cache-busting query on the three
   `SpAM_Task/js/*.js` `<script>` tags in the root `index.html` (they are currently `?v=4.0`) —
   otherwise returning browsers and Pavlovia's CDN serve stale JS
3. Confirm `deployment.mode`, and that `screening_block.prolific_code`,
   `experimental_block.prolific_code`, and `consent.no_consent_code` are all non-empty
   (`verifyConfig` only `console.warn`s on these, it does not throw)

## generate_manifest.py

Browsers cannot list the contents of a server directory, so `task.js` cannot discover which
image files exist at runtime. `generate_manifest.py` solves this: it reads the two stimulus
paths from `task_config.json` (`experimental_trials.stimuli_path` for main images, `catch_trials.stimuli_path`
for practice + catch, scanned twice into separate manifest keys), recursively scans each
directory for `.png` files, and writes `stimuli_manifest.json`.

**Output format** (keys used by `task.js`):
```json
{
  "images":          ["subdir/name.png", ...],
  "practice_images": ["name.png", ...],
  "catch_images":    ["name.png", ...]
}
```

Paths within each list are relative to their respective stimulus directory root, using POSIX
separators (forward slashes), sorted lexicographically. `task.js` prepends the corresponding
`stimuli_path` value (`experimental_trials.stimuli_path` for `images`, `catch_trials.stimuli_path` for
`practice_images`/`catch_images`) to form browser-resolvable URLs.

The script also validates that each set has enough images for the configured thresholds and
prints warnings for any missing or empty directories. Run it once after any change to the
stimulus directories, before testing or deploying.

Both thresholds come from `catch_trials.images_per_trial`: the practice trial has no count of
its own, since `task.js` slices `practiceUrls` to that same value. (`practice_images` and
`catch_images` are two scans of the same directory, so in practice the two checks agree.)

```bash
# from SpAM_Task/
python generate_manifest.py
```

## Key Design Decisions

**Two-stage session structure**: The session is a fixed **screening stage** (optional,
`screening_block`) followed by an **experimental stage** (always present, `experimental_block`).
This replaces an earlier N-uniform-blocks design, which is incompatible with Prolific: their
completion-code API supports exactly one conditional "screen-out" payment gate, not N arbitrary
partial-payment gates. If `screening_block.enabled` is `false`, the screening stage never runs and
every participant goes straight to the experimental stage.

**Stimulus assignment**: Client-side seeded RNG. Seed = `hashString(PROLIFIC_PID)` (djb2). One
session-wide image pool is drawn up front: `buildTrialLists` produces
`(screening_block.num_experimental_trials [if enabled] + experimental_block.num_experimental_trials)`
distinct trials of `experimental_trials.images_per_trial` images each (every image appears in
exactly one distinct trial, no image repeats within a trial), `partitionIntoStages` slices that
flat list into a screening slice and an experimental slice (so no image ever appears in both
stages), and `buildStage` expands each slice into its stage's full trial sequence — repeats and
catch trials are both scoped to that one stage. The single `rng` instance flows through
`buildTrialLists` → `partitionIntoStages` → `buildStage` (× 1 or 2, which internally calls
`insertTrialRepeats`/`insertCatchTrials`) so the entire session sequence is fully reproducible
from the PID.

**Pre-loading**: `jsPsychPreload` inserted immediately before each free-sort trial — loads only
that trial's images on demand, not all 150 at the start.

**jsPsych plugin**: `jsPsychFreeSort`. Images passed as plain URL strings; the plugin wraps
them in `<img>` elements automatically. Output per trial: `data.final_locations` — an array of
`{src: string, x: number, y: number}` objects, where `x`/`y` are pixel coordinates within the
sort area (origin at top-left).

**Responsive layout**: Sort-area dimensions and stimulus size are computed once at page-load
time by `computeLayout(window.innerWidth, window.innerHeight, config)` (utils.js), before any
trial DOM exists — there's no DOM-measurement infrastructure, so sizing is purely arithmetic
against `window.innerWidth/innerHeight`. Width fills `WIDTH_FILL_FRACTION` (0.97) of the
viewport; height fills the viewport minus fixed pixel budgets reserved for the prompt
(`display.min_header_height_px`, above the arena) and the counter + Done button
(`display.min_footer_height_px`, below the arena). Both axes are floor-protected by
`sort_area_min_width/height` for small screens. Stimulus size is
`round(sortW × image_size_fraction)`. This ensures all images render at the same size
regardless of native resolution and the layout degrades gracefully on smaller screens.

jsPsych's own `jspsych.css` vertically centers `.jspsych-content` via `margin: auto`, which
would decouple the visible spacing from `min_header_height_px`/`min_footer_height_px` entirely
(the reserved budgets only shrink `sortH`; they don't create any actual DOM spacing) and can
visually clip content on both edges when the block overflows the viewport. `index.html`
overrides this (`.jspsych-content.spam-freesort { margin: 0 auto; padding-top: 20px; }`) to
top-anchor the content instead, so the header/footer budgets directly determine the visible
layout: content stacks from the top, and any under-budgeted content only ever overflows at the
bottom (predictable, and directly diagnosable by widening `min_footer_height_px`). Scoped to the
`spam-freesort` marker class — each `jsPsychFreeSort` trial (practice, catch, main) sets
`css_classes: 'spam-freesort'` in `task.js` — so non-trial screens (consent, instructions,
transitions) keep jsPsych's default centering.

The plugin's own prompt-to-arena gap (`html_text` wrapper's `margin-bottom`), counter/prompt
`<p>` default browser margins, and Done-button `margin-top/bottom` are all explicitly reset to
small fixed values in `plugin-free-sort-patched.js` (rather than left at browser/plugin
defaults), since default `<p>` margins otherwise add up on both the header and footer sides
without any of it being visible in `computeLayout`'s budget arithmetic.

**Stimuli always start inside a rectangular sort area**: The SpAM literature (Goldstone 1994,
Bracci et al. 2019) arranges stimuli randomly *within* the arena from the start; disengagement
is detected via the `min_trial_duration_ms` floor and the interleaved catch trials, not by a
staging zone. This lets the arena fill most of the viewport width (see "Responsive layout"
above). **Not supported**: the
upstream jsPsych free-sort plugin's `stim_starts_inside: false` mode (images begin in staging
columns outside the arena, roughly halving usable width) and `sort_area_shape: "ellipse"` (a
round arena). Both are hard-coded off (`STIM_STARTS_INSIDE = true` in `utils.js`) and their
code paths have been removed from the patched plugin (`plugin-free-sort-patched.js`) — see that
file's header comment for the full list of deviations from upstream.

**Distance normalisation**: All pairwise Euclidean distances from `final_locations` are divided
by the sort-area diagonal `√(sortW²+sortH²)` → [0, 1]. Removes dependence on screen resolution
and sort-area size, making distances comparable across participants.

**Catch trial design**: `num_catch_trials` (per-stage) catch trials are interleaved among that
stage's own main trials (distinct + repeats) at evenly-spaced interior positions (e.g. trials 3
and 7 in a 10-trial stage). Each catch trial:
- Samples `catch_trials.images_per_trial` (default 10) images from the catch pool via the shared
  seeded RNG, so the selection is reproducible per participant.
- Draws a **target location** from `CATCH_LOCATIONS` (`center`, `top left corner`,
  `top right corner`, `bottom left corner`, `bottom right corner`) via the same RNG.
- Displays the instruction: *"Please place all images on the [target location] of the screen."*

Catch trials detect disengaged participants who are not following instructions. Compliance is
enforced live, not flagged post-hoc: `attachCatchCompliance` (`on_load`) disables the Done button
until `allImagesNearTarget` (every image within `location_tolerance` of the target point) holds,
so a catch trial cannot be submitted non-compliant. `qc_flag` is therefore hard-coded `false` for
catch trials (see "Quality control" below) — `cluster_mean_distance`/centroid are still logged as
diagnostics, not QC criteria.

**Trial-level repeats**: `num_repeat_trials` (per-stage) repeats whole trials *within the same
stage* verbatim (same image set, reshuffled presentation order), for test-retest reliability of
the arrangement response itself — the only mechanism by which an image can appear more than once
per subject. `insertTrialRepeats` may repeat any distinct trial from that stage, and places each
repeat at least `min_repeat_separation` slots after its original, scoped to the stage's own local
slot numbering. This is **additive**, not substitutive: `num_repeat_trials` is added on top of
`num_experimental_trials`, so a stage has `num_experimental_trials + num_repeat_trials`
main-trial slots (plus `num_catch_trials` catch trials). `min_repeat_separation` may be 0 (no
separation constraint) — useful for a screening stage short enough that any positive separation
would be infeasible.

**Quality control — main trials**: Flag a trial if ANY of the following hold:
- `SD(normalised pairwise distances) < experimental_trials.min_pairwise_distance_sd` — all images
  piled up
- `num_moves < experimental_trials.min_move_item_ratio × numItems` — too few drag-end events for
  the number of images shown, indicating the participant barely engaged with the trial

There is no RT-based flag: the `min_trial_duration_ms` floor is UI-enforced (Done button
disabled for that duration), so a too-fast completion is impossible. This per-trial `qc_flag` is
a diagnostic column only; it does not by itself trigger exclusion — see "Live screening" below
for how session-level exclusion actually works.

**Test-retest reliability**: For each completed repeat trial, `computeSpearmanCorrelation`
correlates its pairwise-distance vector against its original's (matched by unordered image-pair
identity, since the repeat reshuffles presentation order) and writes the result to that row's
`reliability` column.

**Live screening**: If `screening_block.enabled`, at the end of the screening stage (exactly one
evaluation point per session — there is no second, later evaluation of `experimental_block`, which
is never assessed or excluded), `evaluateScreening` checks cumulative stats across the screening
stage's own trials against four independent thresholds, each of which may individually be `null`
(disabled) in config:
- Fraction of main trials with `numMoves < experimental_trials.min_move_item_ratio × numItems` `>`
  `screening_block.thresholds.move_ratio_max_fail_rate`
- Fraction of main trials with `sd < experimental_trials.min_pairwise_distance_sd` `>`
  `screening_block.thresholds.distance_sd_max_fail_rate`
- Minimum reliability across completed repeats `<` `screening_block.thresholds.min_reliability` —
  the subject is excluded if ANY single repeat's test-retest R falls below the threshold, not an
  aggregate
- Median reliability across completed repeats `<` `screening_block.thresholds.median_reliability`

The two reliability criteria are additionally skipped (not failed) if zero repeats have completed
yet, independent of whether their threshold is `null`. All comparisons are strict — a value
exactly at the configured threshold still passes.

If any enabled criterion is violated, the participant is screened out: `task.js` sets a
`screenedOut` flag, the remaining (experimental-stage) trials are skipped via a
`conditional_function`-gated nested timeline (chosen specifically because
`jsPsych.abortExperiment()`/`endExperiment()` would also skip the Pavlovia data-upload node,
silently losing the already-collected screening-stage data), and the debrief redirects to
`PROLIFIC_URL_PREFIX + screening_block.prolific_code` instead of
`PROLIFIC_URL_PREFIX + experimental_block.prolific_code`. The evaluation (pass or fail) is also
logged as a synthetic `screening_eval` data row via `jsPsych.data.get().push(...)`.

**Quality control — catch trials**: `qc_flag` is always `false`. Any post-hoc metric (cluster
tightness, move count) can be trivially satisfied without engagement whenever a catch trial's
images happen to spawn compliant by chance, so it would risk a false-positive flag on a
participant who did nothing wrong. The one criterion that actually matters — every image within
`location_tolerance` of the target point (`allImagesNearTarget`) — is enforced live by
`attachCatchCompliance` (`on_load`) instead: the Done button stays disabled until it holds, so a
non-compliant catch trial cannot be submitted at all, making a post-hoc flag redundant.

**Pavlovia saving**: On Pavlovia, the `jsPsychPavlovia` plugin (`lib/jspsych-7-pavlovia-2022.1.1.js`,
loaded from the repo root by a conditional `document.write` in `index.html`, not vendored under
`SpAM_Task/jspsych/`) handles data upload; the `finish` command node is appended to the timeline and calls
`PROLIFIC_URL_PREFIX + config.experimental_block.prolific_code` (or `screening_block.prolific_code`
if screened out) on completion. Locally, `saveData()` downloads a filtered CSV
(practice trials excluded) via a temporary `<a>` element.

## Function Reference

### `utils.js`

| Function | Signature | Description |
|---|---|---|
| `verifyConfig` | `(config) → void` | Validates the parsed `task_config.json` and **throws** `"verifyConfig: <message>"` on any hard failure; `console.warn`s on soft deployment reminders (empty Prolific codes / stimuli paths, non-debug modes only). Called by `task.js` immediately after the config fetch, before any other computation. Checks: (1) section presence + per-key types, with `screening_block.thresholds` validated separately since its 4 fields are `number \| null`; (2) per-field ranges (`images_per_trial ≥ 1`, `min_pairwise_distance_sd ∈ (0,1)`, `min_move_item_ratio ∈ (0,1]`, `location_tolerance ∈ (0,1)`, reliability thresholds `∈ [-1,1]`, fail-rate thresholds `∈ [0,1]`, `num_repeat_trials ∈ [0, num_experimental_trials]`, `mode ∈ {debug,pilot,production}`); (3) cross-parameter arithmetic — `min_repeat_separation` feasibility per stage (via `canSatisfyTrialRepeatSeparation`, checked independently for each stage) and whether `images_per_trial` stimuli of the computed size fit in a square grid inside the *minimum* sort area (main and catch pools separately). Note `deployment.version` is **not** in the schema and is therefore unvalidated. |
| `computeRepeatLayout` | `(t, numRepeats) → {repeatPositions, distinctPositions}` | The structural slot positions `insertTrialRepeats` will use for `t` main-trial slots containing `numRepeats` repeats — derived from `t` and `numRepeats` alone, no RNG or trial data. Repeats go at evenly-spaced interior positions (`round(t/(numRepeats+1) × i)`, nudged forward on collision, capped at `t−1`). Shared so `verifyConfig` can check separation feasibility statically. |
| `canSatisfyTrialRepeatSeparation` | `(t, numRepeats, minSep) → boolean` | Best-case feasibility of `min_repeat_separation`: true if *some* assignment of distinct trials to repeat slots satisfies the constraint, assuming every distinct trial is eligible. **Necessary but not sufficient** — actual runtime feasibility also depends on how many trials end up singles-only (data/RNG-dependent), which `insertTrialRepeats` checks at runtime. Catch trials are not counted toward the separation. |
| `computeLayout` | `(viewportW, viewportH, config) → {sortW, sortH, stimSize}` | Fill viewport width/height (floor-protected by configured min), compute stimulus size as fraction of width |
| `hashString` | `(str) → number` | djb2 hash → positive 32-bit int; seeds the RNG from PROLIFIC_PID |
| `seededShuffle` | `(array, rng) → array` | Fisher-Yates shuffle; non-mutating; accepts a seeded RNG function |
| `computePairwiseDistances` | `(locations, sortW, sortH) → [{src1, src2, distance}]` | All C(k,2) normalised Euclidean distances from `final_locations` |
| `computeCentroid` | `(locations) → {x, y}` | Mean (x, y) of placed images; used to log centroid position in trial data |
| `_targetPoint` | `(targetLocation, sortW, sortH) → {x, y}` | Maps a CATCH_LOCATIONS string to an absolute pixel coordinate (5% from edge for corners) |
| `allImagesNearTarget` | `(locations, targetLocation, sortW, sortH, tolerance) → boolean` | True iff every image is within `tolerance` (normalised diagonal) of the target point; used for catch-trial blocking and QC |
| `computeSD` | `(values) → number` | Sample SD (denominator n−1); returns 0 for < 2 values |
| `computeMainQcFlag` | `(sd, numMoves, numItems, config) → boolean` | True if `sd < experimental_trials.min_pairwise_distance_sd` or `numMoves < experimental_trials.min_move_item_ratio × numItems`. Drives the per-trial `qc_flag` column. |
| `computeSpearmanCorrelation` | `(pairsA, pairsB) → number` | Spearman ρ between two pairwise-distance vectors, matched by unordered `{src1,src2}` pair identity (order-independent). `NaN` if either vector has <2 pairs or zero variance. Throws if the two pair sets don't cover the same image pairs. |
| `evaluateScreening` | `(dataSoFar, config) → {pass, reasons, stats}` | Pure, DOM-free. Evaluates cumulative move-ratio-fail-rate, distance-SD-fail-rate, minimum-reliability, and median-reliability thresholds against `config.screening_block.thresholds` (each individually nullable) and `config.experimental_trials`. `dataSoFar` covers every trial completed in the screening stage so far. Runs exactly once per session, at the end of the screening stage. |

### `task.js`

Single async `DOMContentLoaded` handler. Execution order:
1. Fetch `task_config.json` + `stimuli_manifest.json` in parallel; on failure, replace the page
   body with an error message and return
2. `verifyConfig(config)` — halt with a "Configuration error" page on any hard failure
3. `applyGlobalStyles(config.display)` — injects a `<style>` setting `body`'s
   `background-color`/`color`/`font-family`/`font-size`/`line-height` from the `display` config, so
   every jsPsych screen inherits them without per-element inline styles
4. Parse `PROLIFIC_PID` from URL; halt with error message if absent and not in debug mode
5. Seed RNG: `new Math.seedrandom(hashString(PID))` — **no RNG calls before `buildTrialLists`**
6. Cohort assignment: SHINE variant from `deployment.debug_shine_variant` in `"debug"` mode, always
   `"pre"` in `"pilot"` mode, PID-hash in `"production"` mode. **No validation of the resolved
   variant exists** — `stimuli_manifest.json` is variant-neutral by design (see
   `generate_manifest.py` below) and nothing cross-checks the assigned variant against it or
   against what image files actually exist at `<stimuli_path>/<variant>_shine/`. The `shine_variant`
   column written to each session's data (`task.js` step 10 below) is therefore the **only**
   authoritative record of which image set a participant actually saw — `deployment.mode` and
   cohort assignment logic are not reliable proxies for it. This gap is real: 6 of 47 loadable
   pilot subjects recorded `shine_variant: "post"` despite pilot mode being hard-coded to `"pre"`
   at the time (task_version 3.06), which went undetected until manually audited.
7. Build image URL arrays from manifest keys (`images`, `practice_images`, `catch_images`) + config paths
8. Compute layout via `computeLayout`
9. Build trial sequence: `buildTrialLists` → `partitionIntoStages` → `buildStage` (screening, if
   enabled, then always experimental), flattened into `allTrials`; build a `trialId → trial_number`
   map (1-based, main trials only, matching `trial_type`'s numbering, continuous across stages) for
   resolving repeat references
10. Construct jsPsych timeline: Pavlovia init (Pavlovia only) → consent → fullscreen → instructions
    → before/after examples → practice free-sort → **practice catch trial** (fixed
    `"bottom right corner"`, `trial_type: "practice_catch"`, not analysed) → post-practice
    transition → [preload + free-sort] × n (experimental-stage trials wrapped in a
    `conditional_function`-gated nested timeline, skipped once `screenedOut` is set) → Pavlovia
    finish → debrief (redirects to `PROLIFIC_URL_PREFIX + screening_block.prolific_code` if screened
    out, else `PROLIFIC_URL_PREFIX + experimental_block.prolific_code`)
11. `jsPsych.run(timeline)`

**Session-level fields** (written to every row via `jsPsych.data.addProperties`):

| Column | Description |
|---|---|
| `participant_id` | Prolific PID (or `"debug_participant"` in debug mode) |
| `task_version` | Value of `config.deployment.version` — bump on participant-facing changes |
| `deployment_mode` | `"debug"`, `"pilot"`, or `"production"` |
| `shine_variant` | `"pre"` or `"post"` — which SHINE image set was shown |
| `sort_area_width` | Actual sort arena width in px (filled to `WIDTH_FILL_FRACTION` of viewport width, floor-protected) |
| `sort_area_height` | Actual sort arena height in px (filled to viewport height minus reserved header/footer, floor-protected) |

**Trial-level fields** (written in each free-sort `on_finish`):

| Column | Trials | Description |
|---|---|---|
| `trial_type` | all | `"trial_N"` (main) or `"catch_N"` (catch), 1-based, continuous across stages |
| `trial_index` | all | 0-based position in the full trial sequence |
| `block` | all | Stage label this trial belongs to: `"screening"` or `"experimental"` |
| `num_moves` | all | Total drag-end events recorded by the free-sort plugin (`data.moves.length`); used by the `experimental_trials.min_move_item_ratio` QC flag |
| `is_trial_repeat` | main only | `true` if this trial is a verbatim repeat of an earlier trial in the same stage (see `num_repeat_trials`) |
| `repeat_of_trial_number` | main only | The original occurrence's trial number (the `N` in its `trial_N` value) if `is_trial_repeat` is `true`, else `null`. Directly comparable to `trial_type`/`trial_number` — no re-indexing needed. |
| `reliability` | main, repeats only | Spearman ρ (`computeSpearmanCorrelation`) between this repeat's pairwise-distance vector and its original's |
| `qc_flag` | all | `true` if trial failed any per-trial QC criterion (diagnostic only — see "Live screening" above for actual exclusion) |
| `pairwise_distances` | all | JSON array of `{src_a, src_b, distance}` objects; distances normalised by arena diagonal |

|---|---|

## Running Locally (testing)

The experiment's entry point is `<repo>/index.html` (at the project root, not inside
`SpAM_Task/`). All task code and assets live in `SpAM_Task/`; `index.html` is a thin
wrapper that loads scripts via `SpAM_Task/...` paths. The same `index.html` is served
on Pavlovia, which requires `index.html` at the project root.

The dataset lives at `<repo>/images/{pre_shine,post_shine}/` so analysis sub-modules
can share it. Paths in `task_config.json` are resolved relative to the **project root**
(matching the browser's resolution against `<repo>/index.html`) — both the Python
manifest generator and the browser interpret them the same way.

1. Populate `<repo>/images/pre_shine/` (and later `<repo>/images/post_shine/`) with the
   dataset. Image files are gitignored on `main`; `.gitkeep` stubs are tracked so the
   layout is visible on fresh checkout.
2. Set the active SHINE variant via `deployment.debug_shine_variant` in `SpAM_Task/task_config.json`
   (used in `"debug"` mode) or rely on the PID-hash cohort assignment in `"production"` mode.
   The `experimental_trials.stimuli_path` default `"./images/"` resolves the full main directory
   to `<repo>/images/<variant>_shine/`.
3. Run `python generate_manifest.py` from `SpAM_Task/`. The manifest is variant-neutral (it scans
   `pre_shine/` as canonical and stores paths relative to the variant root, so one manifest serves
   both variants) and records no variant of its own; `task.js` does not validate the
   runtime-assigned variant against it or against anything else — see step 6 of the `task.js`
   execution order above.
4. Serve with a local HTTP server **from the repo root**:
   ```bash
   python -m http.server 8000   # from <repo>/
   ```
5. Open `http://localhost:8000/?PROLIFIC_PID=test123`; set `deployment.mode: "debug"` in
   `task_config.json` for extra console logging and to bypass the missing-PID guard.

### `screening_block`
Block composition + thresholds for the optional screening stage.

| Key | Value | Description |
|---|---|---|
| `enabled` | `true` | If `false`, the screening stage does not run at all and every subject implicitly passes. |
| `prolific_code` | `"C10AANYT"` | Prolific completion code for participants screened out (only meaningful if `enabled`). |
| `num_catch_trials` | 1 | Catch trials interleaved among this stage's own main trials |
| `num_experimental_trials` | 6 | Number of distinct main free-sort trials in this stage |
| `num_repeat_trials` | 2 | Additional (**additive**) verbatim repeats of this stage's own distinct trials, for test-retest reliability. Must be in `[0, num_experimental_trials]`. |
| `min_repeat_separation` | 2 | Minimum number of other stage-local main-trial slots between an original trial and its verbatim repeat. May be 0 (no constraint). |
| `thresholds` | — | Nested object, see below |

Total screening stage: **6 + 2 = 8 main trials** (the `evaluateScreening` denominator) **+ 1 catch**
= 9 trials.

**`screening_block.thresholds`** — each field is a float, or `null` to disable that criterion
entirely (JSON has no `NaN` literal, so `null` is the disabled sentinel). The two reliability
criteria are also skipped, independent of their config value, if zero repeats have completed yet.
All comparisons are strict (`>`/`<`) — a value exactly at the threshold still passes.

| Key | Value | Description |
|---|---|---|
| `min_reliability` | 0.0 | Minimum acceptable Spearman ρ for EVERY individual completed repeat — the subject is screened out if any single repeat's reliability falls below this, not an aggregate. At v4.0's 2 repeats: excluded if **either** repeat has ρ < 0. |
| `median_reliability` | `null` | Disabled. Minimum acceptable *median* Spearman ρ across completed repeats. |
| `move_ratio_max_fail_rate` | 0.13 | Max cumulative fraction of screening-stage main trials allowed to fail the move-ratio check. |
| `distance_sd_max_fail_rate` | 0.13 | Max cumulative fraction of screening-stage main trials allowed to fail the distance-SD check. |

**Fail-rate granularity**: the two rate thresholds are compared against a fraction whose denominator
is the number of *completed screening-stage main trials* — 8 at v4.0 (6 distinct + 2 repeats; catch
trials are excluded). The achievable rates are therefore `0, 0.125, 0.25, …`, so `0.13` means
"**at most one** failing trial out of 8" (1/8 = 0.125 ≤ 0.13 passes; 2/8 = 0.25 fails). Changing
`num_experimental_trials` or `num_repeat_trials` silently changes what these thresholds mean —
re-derive them against the new denominator rather than carrying the numbers over.
